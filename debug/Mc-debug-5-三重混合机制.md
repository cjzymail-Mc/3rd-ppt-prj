## 2. "Pipeline 顺利"是真相还是表象？

**这一节是本评估最关键的节点。**

### Pipeline "顺利"的表面证据
- 跑通无报错
- 自检无致命警告
- 产出文件齐全

### Pipeline "顺利"的真实代价
1. **`_write_chart` 是 Pipeline 的产物，但它埋下了 fix3 数日绕弯路的坑**——Pipeline 跑得"顺利"，是因为 Pipeline 自己不分发，而 `_write_chart` 在分发场景的失败被延迟到了 src/ 阶段才暴露
2. **Pipeline 的 Agents 自检对沉默失败完全无效**——chart bars 消失这类 bug 不抛异常，Agents 无法识别
3. **prompt 结构化管理在移植阶段被部分绕过**——yzr_ppt.py 实际上把 prompt 又硬编码了一份（因为独立性优先，fix2 的决策）

### 结论

> **Pipeline 的"顺利"是一种假象——它把难题延迟到了下一阶段，而不是解决了它们。**

用户感受到"Pipeline 顺利、移植痛苦"，本质是 **Pipeline 没有解决移植阶段的核心难题**（chart 跨机适配性、3D 视角、模板视觉细节）。这些难题不在 Pipeline 的能力范围内，无论 Pipeline 跑多顺，它们都会在移植时爆发。

## 4. 我的建议：第三选项 C

**推翻** 三重混合机制（B）：太激进，会丢失 Pipeline Step 1 在"陌生模板首次分析"上的真实价值
**保留** 三重混合机制（A）：太保守，每次任务都要走流程，token + 认知双浪费

| **Pipeline** | 降级为**可选工具**——仅在"陌生模板 + shape 完全不熟"时启用 Step 1 |
| **Agents 自检** | 降级为**Pipeline 内嵌组件**——不再作为独立"层 2" |
| **三重混合制框架** | 不删除（保留作为"完整流程档案"），但默认不调用 |

### 这与 plan2.md 的关系

plan2.md §3 提的 **5 种任务场景路由表**就是 C 的具体实现：
- 90% 的任务（已知模板修 bug、日常运行、相似新模板）→ Developer 主线，Pipeline 不参与
- 10% 的任务（完全陌生模板首次分析、批量生成多模板）→ 才考虑 Pipeline

C ≈ plan2.md 的优化 1-2 + 重新定义"主线"。

## 5. 为什么 C 比 B 更好（不直接推翻 Pipeline）

### B（彻底推翻）的隐性代价

1. **shape 提取工具丢失**：`pipeline/01_shape_extraction.py` 是个有用的独立工具，扔掉等于以后陌生模板首次分析要重写
2. **架构投资沉没**：Pipeline + Agents 几个月的迭代成果全废
3. **未来回退困难**：如果将来发现确实需要 Pipeline 类工具（比如批量生成 100 套模板），重建成本高
4. **决策不可逆**：删了就回不来；降级（C）保留了未来恢复的可能

### C 的核心优势

1. **保留 Pipeline 的真实价值**（shape 提取作为独立工具）
2. **抛弃 Pipeline 的假象价值**（不再作为强制流程的一部分）
3. **Developer Agent 真正成为主线**（而不是"10% 收尾"）
4. **可逆**：未来若发现降级太激进，能恢复
