# 自检机制解析：为什么 Converter 的交付前自检如此关键

> 基于 Agent-3 Builder 和 Agent-4 Converter 的角色定义、pipeline 工具链、以及 Step3/Step4 实际自检报告提炼。

---

## 1. 全局视角：两层自检构成质量防线

整个工作流中，自检并非单一环节，而是 **两道防线**：

```
Builder (Agent-3)                    Converter (Agent-4)
┌──────────────────┐                ┌──────────────────────┐
│  阶段 B：诊断式自检 │  ──交付──>    │  阶段 B：PPT 自检四步法 │
│  (源码级,逻辑层)   │               │  (产物级,物理层)        │
└──────────────────┘                └──────────────────────┘
    检查 HTML 源码                       检查最终 PPT 产物
    关注：编码/结构/内容                  关注：坐标/可编辑性/视觉/完整性
```

Builder 自检确保 **HTML 源码没有结构性缺陷**；Converter 自检确保 **转换产物与原稿一致且可用**。两层各司其职，缺一不可。

## 2. Converter 自检机制详解

### 2.1 核心设计：先验证 3 页，再生成全部

这是最关键的设计决策。Converter 不会一口气生成 16 页 PPT 然后才检查——它采用 **渐进式验证**：

```
第一轮：只生成前 3 页 (SLIDE_RANGE=1-3)
   ↓
用 win32com 打开 PPT → 逐个 shape 读取坐标/文本/图片
   ↓
与 _layout_manifest.json 对比
   ↓
有问题？→ 修复 export 脚本 → 重新生成前 3 页 → 再检
   ↓
前 3 页通过 → 生成全部页面 → 完整四步法核查
```

**为什么是前 3 页？** 前 3 页通常覆盖了 hero 页（深色背景+大标题）、正文页（文字+图片）、数据页（表格）三种典型布局。如果这 3 页的坐标映射正确，其余页面大概率也是对的。这避免了"生成完 16 页才发现坐标系统性偏移"的灾难。

### 2.2 四步法：覆盖四个正交维度

每次 export 后强制执行，不依赖用户触发：

| 步骤 | 维度 | 检查内容 | 判定标准 |
|------|------|---------|---------|
| **1. 坐标抽样** | 空间精度 | 随机抽 3-5 页，对比 manifest 坐标与 PPT shape 实际位置 | 偏差 > 3pt = 严重 |
| **2. 可编辑性** | 功能可用 | 文本框可点击编辑、图片可选中替换、表格可编辑单元格 | 不可编辑 = 严重 |
| **3. 视觉对照** | 视觉还原 | 逐页与 HTML 截图比对——文字位置、图片填充、表格对齐 | 漂移/重叠 = 严重 |
| **4. 内容完整性** | 数据完整 | 对照 deck_manifest.md 核查标题、段落、图片数量、表格 | 缺失 = 严重 |

四个维度相互独立，不可替代：坐标对了但文本框不可编辑 = 废品；可编辑但坐标偏移 8pt = 视觉不合格；视觉对了但漏了一整个表格 = 内容缺失。

### 2.3 输出物：结构化报告

每次自检生成 `conversion_report.md`，格式固定：

```
| # | 页码 | 维度       | 问题描述           | 严重度 | 状态   |
|---|------|------------|--------------------| -------|--------|
| 1 | 03   | 坐标偏移   | KPI card 偏上 8pt  | 严重   | 已修复 |
| 2 | 13   | 表格       | P1 badge 颜色错误  | 中等   | 已修复 |
```

关键设计点：
- **严重度分级**：严重问题必须在交付前修复，中等问题报告但可接受
- **状态跟踪**：记录"已修复"还是"待处理"，形成闭环
- **可追溯**：用户收到 PPT 时可以直接看这份报告，知道有哪些问题被发现和修复

## 3. Builder 自检机制详解

### 3.1 六步诊断式流程

Builder 的自检更偏向 **源码审计**，分六步：

| 步骤 | 名称 | 做什么 |
|------|------|--------|
| **1** | 三维度诊断表 | 按 CSS / HTML结构 / 内容 三个维度逐项检查，输出结构化表格 |
| **2** | 对标基线 | 与参考模板或前作对比，列出可量化的差距（不是主观感受） |
| **3** | 代码级精确修复 | 每个问题给出：选择器/行号 + 修改前代码 + 修改后代码 |
| **4** | 范围锁定 | 声明"本次检查了什么"和"没检查什么"，避免遗漏盲区 |
| **5** | 分层修复顺序 | CSS架构 → HTML结构 → 内容密度 → 视觉细节 → 抛光 |
| **6** | 双重验证收尾 | 技术（sanity_check.py）+ 业务（逐页对照 brief） |

### 3.2 自动化工具链 (pipeline/)

Builder 的技术验证依托一套 Python 脚本：

```
sanity_check.py           # 统一入口
  ├── check_encoding.py   # 检测弯引号（LLM 最常犯的错）
  ├── check_html.py       # 标签闭合、slide 结构、图片路径、空页面
  └── check_css.py        # 大括号平衡、缺失分号、空规则、重复选择器、class 一致性
```

每个检查器的检查项：

**check_encoding.py**（针对 LLM 生成代码的特有问题）：
- 扫描 HTML 标签内的 6 种非 ASCII 引号字符（`""''«»`）
- 支持 `--fix` 自动替换为 ASCII 直引号
- 这个问题极其隐蔽：弯引号在编辑器中看起来正常，但浏览器无法解析 class 属性，导致整页 CSS 失效

**check_html.py**：
- 11 种关键标签的开闭平衡检查
- section 标签必须有 `class="slide"`
- data-page 编号连续性
- 图片路径存在性验证（本地文件）
- 空 slide 检测（纯文本 < 20 字符）

**check_css.py**：
- 大括号 `{}` 平衡
- 缺失分号检测
- 空规则检测
- 重复选择器检测
- HTML class vs CSS class 一致性（找拼写错误）

## 4. 为什么自检如此关键：从实际经验看

### 4.1 Converter 自检发现的典型问题

从 Step3 转换积累的 8 条教训（C-1 ~ C-8），每条都是自检发现的：

| 问题 | 如果没有自检会怎样 |
|------|-------------------|
| SlideSize 枚举陷阱（3:2 而非 16:9） | 所有页面比例错误，用户打开才发现 |
| extract 与 screenshot 的 CSS 不一致 | 坐标系统性偏移，文字全部漂移 |
| CSS padding 未映射到 TextFrame.Margin | 文字起始位置偏移，看着就"不对劲" |
| rgba 透明度未做 alpha blending | 颜色全错（白色变灰色） |
| `\n` vs `\r` 换行符 | PPT 里换行不生效，文字挤在一行 |
| 文本框宽度未加 buffer | 文字溢出被截断 |

这些问题有一个共同特征：**它们在代码层面看不出来，只有在实际产物中才暴露**。这就是为什么 Converter 的自检必须打开实际的 PPT 文件去验证。

### 4.2 Builder 自检发现的典型问题

从已知 Bug B-1 ~ B-6：

| 问题 | 为什么自检能抓住 |
|------|----------------|
| 弯引号导致 CSS 全失效 | check_encoding.py 逐字符扫描 |
| 绝对定位导致内容重叠 | 三维度诊断表 CSS 维度 |
| overflow:hidden 裁切内容 | 视觉审查 + 禁止规则 |
| 内容稀疏 | 内容维度检查（≥8 条要点） |
| 自检流于形式 | 强制结构化流程，禁止"扫一眼" |

## 5. 设计要点总结

### 要点 1：强制执行，不可跳过

两个 Agent 的自检都标注为 **"强制，不可跳过"**。这不是建议，是硬性规则。角色定义文件中用 `⚠` 符号强调。

### 要点 2：结构化输出，不是主观判断

自检结果必须是**表格**，每行有：页码、维度、问题描述、严重度、状态。禁止"看起来还行"这种模糊结论。

### 要点 3：量化判定标准

- 坐标偏差 > 3pt = 严重
- 纯文本 < 20 字符 = 空页面
- 内容密度 < 8 条 = 稀疏

数字标准消除了"差不多就行"的模糊地带。

### 要点 4：渐进式验证（先 3 页再全部）

Converter 的"先 3 页自检"设计大幅降低了返工成本。如果坐标映射公式有 bug，修复 3 页的代价远小于修复 16 页。

### 要点 5：双重验证（技术 + 业务）

Builder 的自检要求两个维度都通过：
- **技术**：sanity_check.py 通过（编码、结构、CSS 无错误）
- **业务**：逐页对照 brief 检查需求覆盖度

技术验证只能保证"不出错"，业务验证才能保证"做对了"。

### 要点 6：问题驱动的知识沉淀

每次自检发现的新类型问题，会被固化为"已知 Bug 与教训"（Builder: B-1~B-6，Converter: C-1~C-8），写入角色定义文件。下次遇到同类问题，直接在自检中覆盖，形成**正反馈循环**。

### 要点 7：自行修复，不转嫁给用户

两个 Agent 的设计都要求：**自检发现的问题，先自行修复，修复后再验证，循环直到无严重问题，然后才交付**。用户看到的是"这些问题我已经发现并修了"的报告，而不是"这里有 12 个 bug 请你看看"。

## 6. 机制全景图

```
                    ┌─────────────────────────────────────────────┐
                    │            质量保证体系全景                    │
                    └─────────────────────────────────────────────┘

 ┌────────── Builder (Agent-3) ──────────┐   ┌──────── Converter (Agent-4) ────────┐
 │                                       │   │                                     │
 │  自动化工具 (pipeline/)                │   │  渐进式验证                          │
 │  ┌─ check_encoding.py (弯引号)        │   │  ┌─ 先生成前 3 页                    │
 │  ├─ check_html.py (结构/图片/页面)     │   │  ├─ win32com 读取 shape 坐标/文本    │
 │  └─ check_css.py (语法/一致性)        │   │  ├─ 与 _layout_manifest.json 对比    │
 │                                       │   │  └─ 通过后 → 生成全部页面             │
 │  诊断式自检 (六步法)                   │   │                                     │
 │  ┌─ 三维度结构化诊断表                 │   │  四步法核查                          │
 │  ├─ 对标基线（量化差距）               │   │  ┌─ ① 坐标抽样 (偏差<3pt)            │
 │  ├─ 代码级精确修复方案                 │   │  ├─ ② 可编辑性 (文本/图片/表格)       │
 │  ├─ 范围锁定                          │   │  ├─ ③ 视觉对照 (逐页比对 HTML)        │
 │  ├─ 分层修复顺序                      │   │  └─ ④ 内容完整性 (对照 manifest)      │
 │  └─ 双重验证 (技术+业务)              │   │                                     │
 │                                       │   │                                     │
 │  输出: review_report.md               │   │  输出: conversion_report.md          │
 │                                       │   │                                     │
 │  已知教训: B-1 ~ B-6                  │   │  已知教训: C-1 ~ C-8                 │
 └───────────────────────────────────────┘   └─────────────────────────────────────┘

                         ↓ 修复循环 ↓
              发现问题 → 自行修复 → 重新验证 → 无严重问题 → 交付
```

---

## 7. 一句话总结

> 自检机制的本质是：**用结构化的、可量化的、自动化的方式，在交付前把问题拦截住**——而不是靠人工肉眼扫一遍、或者把问题留给下游/用户去发现。它之所以有效，是因为它同时做到了"强制执行 + 量化标准 + 自行修复 + 知识沉淀"四件事。
