## 0. 一句话结论

**不要给"通用 pipeline 的写入器"加复杂度去硬写任意复杂格式**——这条路两个项目历史都走过并否定了；**但"把 `read-selected-shape --full` 细节灌进识别/验收"应该补**，因为读侧加维度便宜、安全、高 ROI。核心是一条**读写非对称原则**。

## 2. 两个项目历史的共识：选择性补、不全面补

「该不该为复杂格式给通用层加复杂度」——两处历史高度一致指向"**选择性补**"。

### 2.1 姊妹项目 Info Classifier 的教训（带文件证据）
- `plan06.md §1A`：**意图层 = 可重复的 80%，不是 100%**；下标/上标/混合字号等 corner case **保留 per-template Python 逃生口，禁强行进通用层**（否则意图层变垃圾场）。其 per-template 脚本 600-950 行被认定为**正常态**。
- `self-check-mechanism-analysis.md`：**自检闭环比格式处理器更 ROI**——与其让通用层"会写复杂格式"，不如让"自检能发现格式问题"。
- `plan05.md §7` 复盘：**不要指望自动优化收敛**——LLM 无显式规则反馈时会作弊收敛（专家审核第 3 轮打回"schema 自动学习"构想）。

### 2.2 本 repo 自己的硬约束
- `feedback_hybrid_workflow.md`：Pipeline 先行 + LLM 精调，**LLM 只在 pipeline 判不了且能提精度时才介入**。
- `feedback_stability.md` / `user_profile.md`：用户明确偏好确定性 Python 控制流，稳定性第一。
- `feedback_acceptance_gate.md` 末节：**自动闭环 = 自动化版红旗 4**，三护栏不可分。

**结论**：给通用写入器加"任意每行多字号/多颜色"能力 = 把 corner case 塞进通用层，两个项目都判为错的方向。

## 3. 核心框架：读写非对称原则

把"复杂格式能力"按 读侧 / 写侧 拆开，结论相反：

| | 性质 | 加复杂度的代价/风险 | 该不该补 |
|---|---|---|---|
| **识别 + 验收（读侧）** | 只读真相提取，确定性 | 低——多读几个字体属性、多比对几维，**无作弊面** | ✅ **该补** |
| **修改（写侧·通用层）** | 生成，要处理无穷格式组合 | 高——通用写入器支持任意每行格式 = 维护噩梦 + 不稳定 | ❌ **不补**，留 per-template 手写 |
| **优化（自动闭环）** | 生成器自改到通过 | 最高——自动化版红旗 4 | ⚠️ **暂不建**，建则死守三护栏 |

**为什么读侧安全、写侧危险**：读侧是把真相看得更清，没有"作弊"空间；写侧一旦让通用器拼任意格式，既复杂又不稳，还会诱发"自动改到通过"的作弊闭环。apparel 已证明写侧正解是 per-template 手写（`src/apparel_ppt.py:1279/1295`），逃生口该在这里。

## 4. 能力缺口清单（该补的 / 不该补的）

### ✅ 缺口 A：读侧维度覆盖不全 —— 建议补（本 plan 的主行动）
**现状**：权威 walker 的 `MERGE_DIMS` 和 `paragraphs_match_signature` 默认 dims 都只有 `(rgb, bold, size)`（`paragraph_runs.py:56` + `layers/runs.py:265`）。
**盲区**：`read-selected-shape --full` 能读但 walker 看不见的——**italic、font_name（NameFarEast/NameAscii 中英混排）、Underline、BaselineOffset（上下标）、行距、垂直锚点**。复杂格式一旦含上下标/下划线/中英混排，**识别和验收当前都罩不住**。
**行动**：给权威 walker（`paragraph_runs.py`）扩维度采集，`check_dims` 按规则选择性断言；**默认仍 `rgb,bold,size` 保向后兼容 + apparel 保绿**。纯加法，对齐 plan-2026-05-28 §3.5.2「只加不改」边界。

### ❌ 缺口 B：通用写入器写复杂格式 —— 不补，且当前行为是对的
`03b _write_text:153` 平铺写入 + 仅【】染色，写不出每行不同字号——**这不是 bug**。现在 `paragraphs_match_signature` 会**检测到**通用器写不出复杂格式并报 FAIL，这正是"该走 developer 移植"的信号。escalation：pipeline 报 FAIL → developer 手写 per-line 格式。**保持这个诚实的失败信号，不要给通用器打补丁。**

### ⚠️ 缺口 C：优化闭环 —— 暂不建（= plan-2026-05-28 Step 5 接力，见 §6）
若读侧补强了维度又上自动闭环，风险放大：闭环可能改 contract/walker 维度作弊收敛。`feedback_acceptance_gate.md:189` 三护栏锁死。详见 §6。

### 🔧 缺口 D：补读侧时别再造第二个 walker（单一真相）
"把 `read-selected-shape --full` 灌进验收"的正确做法是**给权威 walker 扩维度**，**不是**让验收采用 read-selected-shape 的读法。read-selected-shape 用 PPT 原生 `p.Runs()`（不合并、会显示 15~25/℃ 假分段，`read_selected_shape.py:118`），直接拿来会重造 plan-2026-05-28 刚消灭的"两套 walker 漂移"。**read-selected-shape 留作交互式人工调试，权威 walker 是自动化唯一真相。**

## 5. 补读侧必须守的两条约束（否则反噬）

1. **合并维度 ⊇ 断言维度（护栏#1，plan-2026-05-28 §3.5.3）**：要按行断言 font_name，必须把 font_name 加进 `MERGE_DIMS`——否则只差字体的相邻 run 被合并、边界丢失，无法断言。"加一个可断言维度 = 同时加进合并维度"是物理约束。好消息：PPT 假分段（15~25/℃）各维度全同，加维度不会拆开它们，安全。
2. **严格度分级，自由文本不上刚性断言（护栏#4）**：固定标签（评分/数值/温度）→ `must_fix` 按行严卡；GPT 自由文本（优缺点 bullet）run 数随【】浮动 → `warn` 或只断言"标题行样式 + 正文 pattern"。维度补得越细，这条越重要。apparel.json 现有分级是范式。
