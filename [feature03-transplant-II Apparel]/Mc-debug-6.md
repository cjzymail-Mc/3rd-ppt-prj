  下次你想"当场验证一个目录是不是 junction"，可以右键属性看："类型"如果显示 File

  1. "Do not spawn agents unless the user asks" 这条规则是谁加的？怎么改？

  Anthropic 加的，写在 Claude Code 内置系统提示里。你看不到、也没给我加——是

  你能改吗？两条路：

  路径 A: 通过 CLAUDE.md 覆盖（推荐）

  Claude Code 的设计里，CLAUDE.md

  ▎ "Codebase and user instructions are shown below... IMPORTANT: These
  ▎ instructions OVERRIDE any default behavior and you MUST follow them exactly

  意思是你在 CLAUDE.md 里写的规则会压过 Anthropic 默认指令。比如你想让我主动调
  step1-analyzer，只要在 CLAUDE.md 加：

  ## Agent 主动调用规则
  当用户提到"分析 PPT 模板"/"批注新模板"时，**主动 dispatch step1-analyzer
  agent**，无需等用户明确要求。

  我下次会话就会主动调（前提是任务匹配描述）。

  路径 B: 改 agent description 加招呼词

  每个 agent 的 frontmatter 里 description: 字段，加一句 "Use this agent
  proactively when X" — 这是 Anthropic
  设计的"白名单"机制，写了招呼词就允许我主动调。

  例如把 step1-analyzer.md 的 description 从：
  description: 步骤1专属：分析PPT模板 → 提取shape → 生成批注
  改成：
  description: 步骤1专属。Use proactively when user asks about analyzing PPT
  templates, extracting shapes, or generating annotations.

  我看到 proactively 关键词就会更激进调用。

  路径 A vs B：
  - A 适合"项目级强约束"——所有 agent 一起改路由策略
  - B 适合"逐 agent 调优"——只对特定 agent 放开主动权

  你不能改 Anthropic 内置的那条原文——它是 Claude Code
  二进制里的。但你可以用上面两个机制有效覆盖。

  2. 既然 agents 这么好用，越多越好？

  完全不是。这个直觉很危险，反过来才对——好的 agent 体系是少而精。

  越多越糟糕的代价

  经验法则

  ┌────────────┬───────────────────────────────────────────────┐
  │ Agent 数量 │                     状况                      │
  ├────────────┼───────────────────────────────────────────────┤

  ├────────────┼───────────────────────────────────────────────┤
  │ 4-7 个     │ 甜区——覆盖核心专项，每个 agent 都有清晰边界   │
  ├────────────┼───────────────────────────────────────────────┤
  │ 8-12 个    │ 警告区——开始有重叠、决策成本上升              │
  ├────────────┼───────────────────────────────────────────────┤
  │ 13+ 个     │ 反模式——大概率有 agent 几乎不被调用，应该合并 │
  └────────────┴───────────────────────────────────────────────┘

  你现在 5 个，正在甜区，不要再加直到出现具体痛点。

  Unix 哲学的类比

  跟"我应该写多少个独立的 shell 工具？"是同一个问题。GNU coreutils 有 100+
  个工具是因为几十年验证下来每一个都有不可替代的场景。你不会自己一周写 50 个
  bash 工具——多数会用过一次再没碰。

  agent 同理。每个 agent 都该有"我反复需要它"的证据，才值得固化。

  3. Claude 应该能自动构建 agent 吗？系统自带的会越来越多？

  Claude 不会自动构建 agent

  没有这个机制。agent 是人写的——你写或 Anthropic 写，没有"Claude 见到任务自动
  spawn 出新 agent 文件并存盘"这一类自我增殖功能。

  为什么 Anthropic 没做？两个原因：
  1. 质量控制——自动生成的 agent 大概率描述模糊、tool 配置不当，污染主 Claude
  的决策（参见 #2 的"决策成本上升"问题）
  2. 不可观测性——你不会知道你的项目里有什么 agent，难以审计/维护

  系统自带 agent 会增长，但慢

  Anthropic 的 Claude Code 发布迭代里确实会加 agent——比如
  claude-code-guide、Plan、Explore、statusline-setup 这些都是不同时间点引入的。

  但增长很克制：
  - 每加一个都意味着所有用户的 system prompt 多 1 行
  - 通用性必须很强（任何 Claude Code 用户都用得上才值得加）
  - 大概率每年只加 2-5 个

  预测：未来 1-2 年系统级 agent 大概率从现在的 ~7 个 → 10-15 个，不会突然爆炸到
  50+。

  给你的实操建议

  1. 当前 5 个 agent 不要再加，除非碰到具体复用痛点
  2. 不需要改默认"保守 spawn"规则——除非你发现某个 agent
  经常该调没调（这时再用路径 A 或 B 改）
  3. slash command 路线继续走——你的工作流已经稳定，没必要为了"agent
  自动调"重新洗牌
  4. 观察 Anthropic 系统 agent 更新——claude --version 看版本，每次升级看 release
   notes 有没有加新 agent

  最反直觉但最重要的一条：好架构是"少做"出来的，不是"多做"出来的。每加一个 agent
   之前问自己"如果不加，会怎样？"——很多时候答案是"几乎一样"。那就别加。

❌mc-make_chart 函数，导致导量 chart 残留在 Excel中；这个需要解决（claude的方案更好） (暂时不动生成函数 make_chart了)❌

你在 yzr/zxh/apparel 这些 py 中 make chart时，会将残留在源数据Excel文件中的chart删除，保持文件整洁；

我觉得这个功能挺好，不过，你是如何做到：即使没有在视觉上看到chart，也能执行复制、删除？

我的意思是，我自己在 Function_030.py 的 make_chart函数中，必须使用 zoom 将 Excel 整体缩放，让 chart显示处理，才能顺利完成操作；

如果因为缩放问题，导致chart被滚动到可视范围之外，就会导致复制、 删除等操作失败

你不用改任何代码，我们仅先讨论这个问题的原因和技术路线



--------------------------

我看清两边代码差异了。给你解释一下根因和技术路线。

  根因：两套完全不同的 chart 访问路径

  老路线（Function_030.make_chart line 2471~）—— UI Selection 路径

  temp_list[p_i].select()            # line 2531/2552 用 Range.Select 导航
  mc_book.selection.end('down').select()
  mc_book.selection.end('right').select()
  ...
  chart_cell.select()                 # line 2984 选中 chart 旁的 cell
  mc_chart1.api[0].Copy()            # line 2997 然后 Copy

  它本质是**"先选中、再读当前 Selection 状态"**：
  - 用 xlwings.search("图表1") 找 chart 锚点
  - 用 Range.Select() + selection.end() 一步步导航出 control_count / n_j
  - chart_left/chart_top 来自 mc_sht.cells(...).left/.top

  问题：Excel COM 里的 Range.Select / Selection.End 强依赖 ActiveWindow —— 那个
  Range 必须在视口里才能稳定 Select。一旦 chart 滚到屏幕外，select 要么报
  0x800A03EC，要么静默选错。所以你写 Excel_zoom(mc_sht, 30) 把 sheet 缩到 30%
  让所有 chart 进入视口，是绕开 UI 限制的折中。

  新路线（yzr/zxh/apparel/_ppt_shared.make_chart_for_*）—— 对象引用路径

  mc_chart1 = mc_sht.charts.add(chart_left, chart_top, ...)   # 直接拿引用
  mc_chart1.set_source_data(mc_sht.range(...))
  ...
  mc_chart1.api[0].Copy()           # 通过对象引用 Copy
  _tmp_chart.delete()               # 通过对象引用 Delete

  完全不走 Selection：
  - chart 锚点 mc_cell 由外层传入，不靠 search()
  - charts.add() 返回 xlwings Chart 对象 —— 同时持有 .api[0]（ChartObject）和
  .api[1]（Chart）两层 COM 引用
  - Copy/Delete 都是 ChartObject 上的成员方法，receiver = self，不读
  ActiveSelection

  为什么对象引用免疫可见性

  Excel COM 里 chart 有两套访问入口：

  ┌────────────────────────────────────┬──────────────┬────────────────────┐
  │                路径                │     依赖     │      失效条件      │
  ├────────────────────────────────────┼──────────────┼────────────────────┤
  │                                    │ ActiveWindow │ chart              │
  │ UI Selection (Range.Select →       │  + 视口 +    │ 不在视口、Window   │
  │ Selection.Copy)                    │ 选中状态     │ 不 active、Sheet   │
  │                                    │              │ 没 select          │
  ├────────────────────────────────────┼──────────────┼────────────────────┤
  │ 对象引用                           │ 只要         │ 工作簿被关、Sheet  │
  │ (Worksheet.ChartObjects(n).Copy()  │ Worksheet    │ 被删               │
  │ / xlwings .api[0])                 │ 对象还活着   │                    │
  └────────────────────────────────────┴──────────────┴────────────────────┘

  ChartObject.Copy() 这个 COM 方法的内部实现根本不查 ActiveWindow ——
  它对自己持有的内部 chart 句柄直接走"复制到剪贴板"流程。所以 chart
  在不在视口里都无所谓，甚至 sheet 没被切到当前页都能 Copy（不过为了 OLE
  渲染保险，新代码还是会先 mc_sht.select()）。

  Delete 同理：ChartObject.Delete() 是按对象身份销毁，不需要先选中。

  你的情况：为什么必须 Excel_zoom

  不是 Copy() 本身需要可见，而是它前面那串 Range.Select 需要可见。make_chart
  里的导航逻辑（selection.end('down') / chart_cell.select()）每一步都要求当前
  Range 在视口里，缩放到 30% 才能让所有 chart 同时塞进一屏。

  注释 line 2407 里那句 "GPT已经把原因解释了，必须显示才能复制" —— GPT
  当时给的诊断方向其实不准。真正的限制不是 Copy 必须显示，而是 Select
  必须显示。Copy 是被 Select 拖累的。

  升级路径（如果将来想拆掉 Excel_zoom）

  把 make_chart 的工程模式向新代码看齐，4 步：

  1. 锚点由外层传入 mc_cell，不用 search("图表i") 扫工作表
  2. 用 mc_sht.charts.add(...) 拿对象引用，丢弃 temp_list[p_i].select() 路径
  3. 所有 Copy/Delete 走 mc_chart1.api[0] / _tmp_chart.delete()
  4. 删掉 Excel_zoom —— 自动免疫缩放/滚动

  这等于把 yzr/zxh/apparel 的工程模式回灌到老代码，换来的代价是 make_chart
  要拆成 make_chart_for_xxx 多份（每个模板一个，外层传锚点）。短期不改也行，因为
   Excel_zoom 是有效的折中——只是技术债。

  卡点根因：他们做了两层（Python 工具 + Agent 编排），缺了 3rd-ppt-prj

  用本项目经验对照，3 条核心建议：

  1. 一脚本一模板，不要做"通用填充器"

  本项目 yzr_ppt.py / zxh_ppt.py 是按模板分文件，共享代码在
  _ppt_shared.py。他们应该改成 fang_caixia.py、下个客户.py，每个独立 Clone
  模板页 + 槽位逻辑硬编码；通用的 COM dispatch / 表格行复制 / 字体设置进
  _office_shared.py。
  为什么：通用填充器永远写不完，因为模板的"段落 run 注入 / 表格行增删 /
  加密自检"边界条件穷举不完；按模板固化后每个文件 300
  行可控、新模板加文件不改老文件。

  2. 生产期把 Agent 拿掉，回到 python Main.py 模式

  他们现在让 Archivist Agent 做填充，等于每次跑生产都要起 LLM
  session（慢、不确定、依赖 Claude Code 环境）。本项目 Step3 完全是确定性
  Python，LLM 只在 PDF 语义提取那一步（结构会变的部分）出现，输出结构化

  生产更确定（模板槽位数量固定、PDF 结构相对稳定），更不需要 LLM 全程介入。LLM
